# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

**Pheeme** — an open-source (MIT), multi-platform Tauri 2 desktop client for Gmail and Google Calendar (React + Rust + SQLite). Users bring their own Google Cloud OAuth client (BYOC), so the app costs nothing to run. Domains: `pheeme.app`, `pheeme.email`. (The bundle identifier is `app.pheeme.desktop`, the crate is `pheeme`, and the GitHub repo is AlexGenovezos/pheeme.)

The [design](docs/superpowers/specs/2026-10-31-mail-calendar-client-design.md) sets product scope and priorities. The [architecture guide](#architecture) describes the current implementation. The [original Gmail project plan](Gmail%20client%20project%20plan.md) is a historical archive.

**Current state (v0.34 beta).** Pheeme supports offline-first, multi-account Gmail, Google Calendar and Tasks. Mail integrates with Drive for links and attachments. Calendar can show weather forecasts. A local MCP server connects assistants, and mods add commands and integrations.

### Rust / Database

```bash
# From src-tauri/
cargo check --manifest-path src-tauri/Cargo.toml
sqlx database create
sqlx migrate run
cargo sqlx prepare   # Regenerates .sqlx/ offline query cache (required after schema changes)
```

SQLx uses **compile-time query validation** against `.sqlx/` offline cache. After any schema or query change, run `cargo sqlx prepare` before committing.

### Database location

SQLite DB is created at the platform app data dir at runtime. Migrations live in [src-tauri/src/db/migrations/](src-tauri/src/db/migrations/).

## Architecture

### Two-Process Model

- **Frontend** (`src/`) — React 19 + TypeScript, built with Vite. Communicates with Rust via Tauri's `invoke()` IPC, always through the typed `call` in [src/lib/ipc/call.ts](src/lib/ipc/call.ts): every command is an entry (name, argument object, result) in the `Commands` map in [src/lib/ipc/commands.ts](src/lib/ipc/commands.ts), and the wrappers live one file per domain in `src/lib/ipc/` (accounts, mail, labels, search, senderRules, stats, compose, contacts, calendar, calendarEvents, weather, tasks, assistants, settings, support, events), re-exported by the barrel [src/lib/tauri.ts](src/lib/tauri.ts) (feature folders keep their own `api.ts` over the same `call`). Events are typed the same way: `AppEvents` in `src/lib/ipc/events.ts` maps each event name to its payload, and `listen` from `src/lib/tauri` takes its payload type from it.
- **Backend** (`src-tauri/src/`) — Rust Tauri app. Exposes commands, manages DB, handles Gmail API and OAuth.

| `db/` | All SQLite CRUD via SQLx — one file per entity (messages, threads, labels) |
| `commands/` | Tauri command handlers (the IPC surface the frontend calls) |
| `gmail/` | Gmail REST API client. `client.rs` sends every request (`execute`: slots, retries, the pure `build_request` and `classify`); its priority comes from scopes, not method names: `user_action` for what the user is waiting on, `background` for bulk work (the backfill, preloads), the innermost winning. `quota.rs` paces requests under the per-user quota (`QuotaLimiter`); `auth.rs` is OAuth (PKCE + loopback redirect); `usage.rs` counts, in memory, each account's Gmail quota units per minute for the last hour by source (`usage_source` scopes: the outbox in `sync/manager.rs`, assistants in `local_api`; else by priority) and Gmail's rate-limit refusals, for Settings › Accounts (`gmail_quota_usage`) |

it needs its own incremental consent (`ClientChoice::CalendarColors`, `auth::CALENDAR_LIST_SCOPES`: `calendar.calendarlist`), `missing_scope` until allowed (the sidebar's palette button, `src/calendar/CalendarColor.tsx`, asks for it and saves the colour after). `availability.rs` answers the editor's planner live, never cached: one `freeBusy.query` for the account (`primary`) and each guest, per person busy intervals or `unknown` with Google's reason; it needs its own incremental consent (`ClientChoice::Availability`, `auth::FREEBUSY_SCOPES`: `calendar.events.freebusy`, since `freeBusy` doesn't accept `calendar.events`), `missing_scope` until allowed. It also holds the cached-calendar rules the assistants' `find_free_time` uses (`busy`: timed, not declined or marked free, merged; `free_slots`: inside working hours per day), apart from the planner's own. Commands wrap in `user_action`. `reminders.rs` fires each shown event's notification reminders (its own, else the calendar's defaults; all-day events only their own) as desktop notifications: planned from the cache 24 h ahead, re-planned on `calendar:updated`/`calendar:access` and before each fires, a reminder up to 5 min late still fires once (sleep, late launch), what fired is kept in `calendar_reminders_fired`; declined events, hidden calendars, Settings › Notifications (Event reminders switch, schedule) and OS permission skip it. `desktop.rs` shows it (`NotifyTarget::Event`); a click opens Calendar mode on the event's day with its popover, and an event with a video call gets a Join button (D-Bus action, `UNNotificationAction`, toast button) that opens the call. `templates.rs` keeps event templates in SQLite (`event_templates`): save (a taken name, ignoring case, is `exists` unless replacing), rename, delete and list, local only, behind the `event_templates` commands |

Emits `tasks:updated` and `tasks:access`. `writes.rs` (add, edit, complete, delete, reorder, indent, move to another list; create, rename, delete lists) goes straight to the Tasks API, not the outbox, and caches only what Google confirms; a write holds the account's sync gate so a running sync can't cache an older version. `gmail/tasks.rs` is the API client. ### Frontend State

The main Zustand stores:
- `accountStore` — connected accounts (load, upsert, remove)
- `mailStore` — the active mailbox or search results (paged, optimistic patches), reloaded on `sync:*` events; search combines instant local matches with background Gmail pages
- `labelStore` — per-account labels, label counts and category counts, plus the All Inboxes unread count
- `threadStore` — thread-detail cache with prefetch; evicts on `sync:messages_updated`
- `inboxTabsStore` — per-account hidden Inbox tabs (Primary is always shown)
- `downloadStore` — the mailbox download (an account's first sync and the backfill): `get_sync_progress` every 2 s while one runs, else on `sync:started`; the corner card it feeds can be closed until another account starts downloading
- `uiStore` — active mailbox, search text and account scope, selected thread, multi-select, pane layout
- `calendarStore` (`src/calendar/`) — Mail or Calendar in front (`mode`), the Day/Week/Month view (both remembered), the day shown, each account's calendars and access, the events of the months around the days on screen (kept in memory, so switching views or stepping draws at once; a day outside them shows only once its events are read), the open event popover, and the email pinned beside the calendar (`pinned`, with the time Day/Week open scrolled to)
- `tasksStore` (`src/tasks/`) — every account's task lists and tasks access, each list's tasks (read while the Tasks panel is open), the dated tasks of the days the calendar shows, the task open for editing, and whether the panel is open (remembered); changes show at once, go straight to the Tasks API, and snap back with a toast if Google refuses
- `editStore` (`src/calendar/`) — calendar editing: the new event being placed (quick create), the open editor, the question a write waits on (`ask`), an event being dragged or saved somewhere new, events hidden while being deleted, and calendar search
- `composeStore` (`src/compose/`) — open compose panels (autosave, close prompt) and sends waiting out undo or Gmail's confirmation (the pending-send tracking, Undo and failed-send notices are in `sending.ts`); a refused or undone send reopens its panel
- `signatures` (`src/compose/signatures.ts`) — per-account signature choices for new messages and replies/forwards (Gmail's, the account's own, or none), saved in `app_settings` (`compose/signatures.rs`, which also signs AI assistants' drafts) and mirrored in localStorage, and the last fetched Gmail signatures (`users.settings.sendAs`) in localStorage. The signature sits in the body as one `div.gmail_signature` block (`SignatureNode`), above the separately held quote; Settings › Compose edits them

Calendar mode (`src/calendar/`) replaces the mail panes when `calendarStore.mode` is `calendar` (Mail | Calendar switch in the sidebar footer, `mod+1`/`mod+2`). Dates are `YYYY-MM-DD` strings and times UTC ms shown in the first account's Google Calendar time zone (`dates.ts`); `layout.ts` places events (overlap columns, all-day band, month cells with "+N more"). In Calendar mode the conversation commands aren't registered and mailbox commands lose their keys, so `d`/`w`/`m`/`t`/`j`/`k`/`g` are free for the calendar. Editing follows the website: click or drag empty hours/days for the quick-create popover (`QuickCreate.tsx`); `c` and Create open quick add (`QuickAdd.tsx`), where a sentence like "Lunch with Sam Friday at noon at Joe's /work" becomes the event, highlighted as it's read (`sentence.ts`: chrono-node and rules, no AI; time, repeat, length, place after "at", people after "with" offered from contacts and invited only when picked, `/calendar`, and "todo …" for a Google Task), with Undo on the toast; More options or `e` for the editor dialog (`EventEditor.tsx`, its model and the only-what-changed `EventEdit` in `eventForm.ts`; for a timed event with guests, Check availability opens `AvailabilityPlanner.tsx`: you and each guest as busy rows across 7:00–21:00 of a day, click or arrow keys to move the event, and Next available time, the first slot within 9:00–17:00 Mon–Fri over 14 days where everyone whose availability is known is free; the constants and the slot search live in `availability.ts`), drag to move or the bottom edge to resize (`drag.ts`, targets marked `data-cal-drop`), Delete/Backspace, Duplicate, Save as template… and Copy to from the popover, `/` to search (`CalendarSearch.tsx`). Event templates (`templates.ts`, `templatesStore.ts`; kept by Rust's `calendar/templates.rs`, never sent to Google) hold an event's details but not its time or repeat: Save as template… names them (`SaveTemplate.tsx`), a quick add sentence starting with a template's name starts from it (the `template` span; the rest of the sentence still sets the time, place, people and `/calendar`) and the templates show as buttons under the field, the palette has "New event from template: …" per template (`calendar.template:<id>`, counted in usage stats only as `calendar.template`), and Settings › Calendar renames and deletes them (`TemplateSettings.tsx`). Guests' answers (the Yes/Maybe/No options and the "2 yes, 1 maybe" tally) are `rsvp.ts`, shared by the popover and the invite card. Events with a video call show a camera before their title, and the popover a Join button for any provider (`meeting.ts`; `shift+j`, `calendar.join`). `actions.ts` asks the repeating-event and send-to-guests questions (`EditPrompt.tsx`), writes, and on `conflict` reloads; only events with `canEdit` show edit affordances. Other time zones (up to two, Settings › Calendar, `zoneSettings.ts`, localStorage; names and offsets in `zones.ts`): Day and Week give each its own column of hour labels left of the calendar's (`gutterTimes`, :30/:45 where the zone is off the hour; `--cal-zone-columns` widens `--cal-gutter`), and the popover gives a timed event's time in each, plus its own zone when that keeps another clock. Typing a time in the command palette ("3pm PT in Athens", "15:00 London to Tokyo", "noon in New York") answers in a first row that Enter copies (`zoneConvert.ts`: chrono-node, IANA city names and a few abbreviations; `convertCommand.ts`). When the computer's zone keeps another clock than the calendar's, `TravelNote.tsx` says so at the foot of the sidebar, offers to add the computer's zone, and stays dismissed for that zone pair; the Google Calendar zone itself is never changed. The preview's calendar zone is `?calendarZone=`.

Weather (`src/weather/`, off by default): Settings › Calendar holds the switch, the home location (typed, or found from the calendar's time zone) and °F/°C (`weatherSettings.ts`, localStorage). The weather is drawn by `WeatherArt.tsx`: an SVG scene per kind, clouds as clusters of shaded spheres laid out from a seed (the day, so each day's sky differs but redraws the same), a glowing sun, rain and snow as particles (more the heavier it falls), a flickering bolt. With Settings › Calendar › Animate weather on (or the pause/play button on the popover's forecast), it moves in the popover and on the day or month week pointed at; off, or with reduced motion, it holds still. `DayWeather` puts the home forecast in each day's header (a fixed slot from the first frame; high and low, the high alone, or the icon as the day narrows) and a month cell's date row; `EventWeather` adds a card with the forecast for an event's place to its popover (the same box loading, loaded or not found) when its location could name a town and its day is in the forecast. In Day and Week, the hourly forecast (the same request, Rust turning each hour into a UTC instant) is drawn in the hours themselves: `hourly.ts` turns it into runs per day in the calendar's zone (sun in daylight, rain, snow, storm, fog; cloudy hours draw nothing), `HourWeather.tsx` puts one faded band per run behind the events, each seen through a window pane (`pane/`: one seeded scene per kind that `Pane.tsx` draws on a canvas: rain as beads of water, drops hitting and drips running down; a storm's lightning; snow falling outside with crystals on the glass; fog as misted glass with mist drifting behind; sun as slanting light and dust), and the header's tooltip says them in words. The bands are still pictures; `motion.ts` plays a day's for 8 s when the grid shows new days or the pointer moves into it (then each scene winds down by itself: drips come to rest, snow and mist slow to a stop), never with Animate weather off, reduced motion or the window in the background, so a calendar at rest runs no animation.

Calendar inside Mail: a message with a `text/calendar` part or `.ics` file (`src/mail/invitePart.ts`, from its attachment list, so the card holds its place from the first frame) gets the invite card at the top of the conversation (`InviteCard.tsx`): what, when, where (Join for a meeting link), organizer and guests' answers, Yes / Maybe / No and More options (a note; "only this event" for a series), and a mini day view of the hours around it from every shown calendar with clashes named (`invite.ts` holds the rules: the live event over the email's, the cancelled/moved/updated notice, clashes). It answers on the calendar's copy when cached, else by UID through `respond_to_calendar_invite`; an account without calendar access sees the invitation and an Allow button. **Open … in Calendar** and **Create event from email** (`mailActions.ts`; toolbar, More actions, palette, `shift+e`) switch to Calendar mode on that day with the email pinned in a left column (`PinnedEmail.tsx`: the card, the start of the text, Unpin, Back to Mail). Create event fills step 5's editor from the email (`fromEmail.ts`): the subject without `Re:`/`Fwd:`, the thread's people but you, the start of the email's new text (the quoted thread and signature left out) and a labelled link back to Gmail, and the first time `chrono-node` finds in the subject and new text (then the quoted thread, minus its "On … wrote:" lines) (relative to when it was sent; a date alone is all-day), else the next half hour, on the receiving account's calendar. The unnamed `text/calendar` part isn't listed as an attachment. Clicking an `.ics` file (or the card's Add to calendar, for a file that isn't an invitation you're a guest of) opens **Add to Google Calendar** (`AddFromFile.tsx`, rules in `calendarFile.ts`): every event in the file (Rust's `calendar/file.rs`, `ics::parse_all`), ticked, on a calendar you pick, added as plain copies through `events.import` (no organizer or guests, nobody emailed); a single invitation you're a guest of is accepted instead, and events already on a calendar (same iCalUID) show where.

Google Tasks UI lives in `src/tasks/`. The Tasks panel (`TasksPanel.tsx`, with `TaskRow.tsx` and `TaskEditor.tsx`) sits at the right edge in both modes, opened from the rail beside it or `mod+shift+t` (`view.toggleTasks`): every account's lists, with add, edit (title, details, due date), complete, delete, drag to reorder, indent/outdent (`mod+]`/`mod+[`) and move to another list, plus create/rename/delete lists; an account without access gets Allow, one whose Tasks API is off gets a link to turn it on. `outline.ts` holds the ordering rules (completed split, where a drag or indent lands as `parent`/`previous`, where a new task's field sits: `outlineRows`). Dated tasks show on the calendar through `DatedTasks.tsx` (`useDatedTasks`, `TaskChip`) and `gridLayout.ts`, which places them in the first free row of their day after the events; the calendar sidebar's task-list ticks (`SidebarTaskLists.tsx`) choose which lists show. The panel opens with **Today** (`TodaySection.tsx`): every open task due today or earlier (`tasks_due_through`, the store's `due`). **Plan today** (`PlanToday.tsx`, `planStore.ts`, `tasks.planToday`) walks those one at a time, overdue first, and each gets a decision (Today, Tomorrow, Pick a day, Book a time, Done, Drop); it opens on its own the first time the app is used each day when something is due (`plan.ts` holds the rules; only `pheeme.tasks.planned` is stored). **Book a time** sets the due day and opens Google Calendar on the web there, since only Google can make a task block (the API refuses `focusTime` for personal accounts); Google's blocks come back as `focusTime` events, which `calendar/task_block.rs` marks with `taskLink` (not editable), and the calendar draws a matched block as its task, with a tick, in place of its dated chip.

The sidebar footer (`src/shell/SidebarFooter.tsx`, the same in Mail and Calendar) holds the Mail | Calendar switch, Settings, Stats, Add account and Check for updates.

Settings is a dialog over the app (`src/settings/`). Pages, sections and rows are declared as data in `src/settings/pages.tsx`: a new setting is one `SettingDef` there. A page's part can also be a block that draws itself (`SettingsBlockDef`), so per-account parts sit on the page they belong to (Signatures in Compose, Sender rules in Inbox, Diagnostics in About). Keyboard shortcuts come from the command registry; user rebindings are overrides stored by `src/keyboard/bindings.ts`, so label a button with `useKeybinding(commandId)` rather than a literal key. Browser storage goes through `src/lib/storage.ts` (reads and writes that never throw).

Floating panels share `src/components/ui/`: `placement.ts` (pure, tested: clamp to the window, beside an anchor, under or over a field), `usePopover.ts` (`usePopover` for a panel opened at a point: kept on screen, closed by an outside press or window blur, focus moved in and back; `useDismiss` for the dismissal alone), `useDialogFocus.ts` (the Modal focus trap, shortcut suspension and focus return, shared by Settings and the speed reader, which key-handle for themselves) and `Surface.css` (`popover-surface`, `dialog-surface`, `dialog-scrim`: the border, radius, background and shadow every popover and dialog shares, at zero specificity so a component's own rule wins). New popovers and dialogs use these instead of pasting the declarations. Everything in the bottom-right corner draws through `CornerCard` (`src/components/ui/CornerCard.tsx`): toasts, and the cards `src/shell/CornerNotices.tsx` pins under them (offline, Gmail slowing sync, each account's failed sync or sign-out with Sign in again, the mailbox download from `downloadStore`, the update offer). Gmail filters UI lives in `src/filters/`: Settings › Filters (`FiltersSettings.tsx`, every filter per account as its search and its actions in words, with Edit, Delete with Undo, and Create filter) and the editor dialog (`FilterEditor.tsx`, mounted after Settings so it opens over it; form rules in `form.ts`), which Filter messages like these (`likeThese.ts`, the conversation's More menu and the palette's `conversation.filter-like-these`) opens with the sender in From. Label UI lives in `src/labels/`: the label tree (nesting by `/` in names), palette and chip colours, the searchable picker behind Label as… and Move to…, and the create/edit/delete dialogs. The sidebar's Labels section (the tree rows and each label's menu) is `src/shell/sidebar/Labels.tsx`, beside the sidebar's keyboard navigation (`keys.ts`).

Compose panels dock at the bottom of the window (`src/compose/ComposeHost.tsx`); the TipTap editor is lazy-loaded with the panel. The From row is a picker when there's a choice: the account's send-as addresses (`src/compose/sendAs.ts`, kept from the last fetch), and for a new message every account's; with Gmail's signature chosen, each alias brings its own. Send later (the menu beside Send, or the palette's `compose.sendLater`) saves the message as a Gmail draft, closes the panel and opens Gmail's Drafts on the web (`gmailDraftsUrl` in `composeStore.ts`; Gmail web can't open a draft from its API id), where Gmail's Schedule send picks the time; Pheeme keeps no schedule. The formatting bar under the text (`FormatBar.tsx`, shared with the signature editor in Settings › Compose) has Gmail's options: undo/redo, font, size, bold/italic/underline, text and background colour (Gmail's 64-colour palette), align, lists, and under More indent, quote, strikethrough and remove formatting, plus the link; its menus are popovers opening upward (`floating.tsx`), so the bar keeps one row. `formatting.ts` holds the TipTap extensions, which write what Gmail sends so other clients show it the same: `<font face|size|color>`, a `background-color` span, `text-align`/`margin-left` styles on paragraphs and Gmail's inline-styled `<blockquote>` (never a class: `split_quote` treats `gmail_quote` as the quoted original), and read them back from saved drafts; Gmail's keys where they don't clash (`GMAIL_KEYS`: `mod+shift+x` strikethrough, `mod+\` remove formatting, `mod+[`/`mod+]` indent, `mod+shift+9` quote, `mod+shift+l/e/r` align). Insert emoji (`EmojiButton.tsx` in the footer) lazy-loads `EmojiPicker.tsx` with Unicode's list (`unicode-emoji-json`, emoji up to 15.0; search and recently used in `emoji.ts`); it stays open for several picks. A panel is a `data-owns-keys` region, so single-key shortcuts don't fire inside it. Mail actions (archive, trash, star, important, read, labels, reply, new message) are re-exported from `src/mail/actions.ts`, shared by buttons, menus and shortcuts (Report spam, `!`, is in the conversation's More menu and the row menu: it adds SPAM and removes INBOX, leaves the list (search results too), skips conversations in Spam, Trash or Drafts by their own labels, and its Undo gives INBOX back only to those that had it; in Spam the Archive slot is Not spam); they live beside it by topic: `change.ts` (what they share: `apply`, targets, opening a conversation), `mutations.ts`, `labelActions.ts`, `categories.ts`, `navigation.ts`, `searchActions.ts`, and `src/compose/respond.ts` (reply, new message). Importance (Gmail's `IMPORTANT` label, which rows already carry in `systemLabelIds`, so no new DTO field) is `setImportant` in `mutations.ts` through the outbox with Undo, changing only the conversations not already in that state (`+`/`=` mark, `-` clears; `=` is the hidden `conversation.mark-important-alt` command, since a command has one key; in the Important mailbox Not important takes the row out (in a search it stays until the next reload, like archive); Spam and Trash rows can't be marked, since Gmail shows only their SPAM/TRASH label there); `importance.ts` holds the label rules and `ImportantMark.tsx` is the chevron every list row reserves at the start of its sender (filled when important, an outline on hover, click toggles), so no row changes width in either density. The More menu, the row menu and multi-select swap one item's words between Mark as important and Mark as not important. Each action's optimistic changes go through one `OptimisticOp` (`src/mail/optimistic.ts`), which patches the list rows, cached conversations and unread counts and releases them all when the command settles; the stores hold them over reloads with `PendingChanges` (`src/store/pendingChanges.ts`). Clicking an attachment (or Space on it) opens a Quick Look-style preview over the blurred app (`src/mail/preview/`): PDFs (pdf.js; the newer JavaScript built-ins it calls, which an older Mac's WebKit lacks, come from `pdfjsPolyfills.ts`, loaded before it in the window and in its worker `pdf.worker.ts`, and its test fails when a pdf.js upgrade needs another), Word (docx-preview, in a script-less sandboxed frame), PowerPoint (`@aiden0z/pptx-renderer`, slides mounted as they scroll into view, external media blocked), spreadsheets and CSV, images and text, each reader lazy-loaded; opening a conversation prefetches its attachments into the disk cache. Browser preview (`npm run dev`) answers every command from `src/preview/` fixtures, which mutate and emit `sync:messages_updated` like the app.

Unsubscribe in the conversation (`src/mail/unsubscribe.ts`, `UnsubscribeDialog.tsx`): every `MessageDetail` carries `unsubscribe` (`one_click`, `link`, `email` or `none`, from its `List-Unsubscribe`/`List-Unsubscribe-Post` headers by `senders::options` in `mail/dto.rs`), so `MessageCard` draws the Unsubscribe button beside the sender from the first frame (not on your own mail or drafts); it asks "Unsubscribe from <sender>?" The speed reader (`src/speedread/`) flashes one word at a time from emails that are mostly prose. `text.ts` decides which emails qualify and extracts their paragraphs, `words.ts` holds the focus-letter and pause rules, and its settings (`settings.ts`) are shared by the reader dialog and Settings › Reading.

### Database Schema Summary

Twenty-nine tables, plus the `messages_fts` full-text index.
- `accounts` — Account identity and Gmail history_id for sync (no tokens; those are in the keychain), plus the user's order (`position`, dragged in the sidebar) and colour (`color`, 1–12: `--color-account-N`, picked from the account's dot)
- `labels` — Gmail labels with message/thread unread/total counters
- `threads` — Conversation rows, derived from their messages by `threads::recompute_threads` (never written directly by sync)
- `thread_labels` — Thread/label membership; label listing uses keyset-paged `list_threads`
- `thread_versions` — Per account, a number `recompute_threads` bumps whenever its threads or their labels change, so `label_counts` reuses its last count until then
- `label_thread_counts` / `inbox_unread_counts` — The sidebar and tray counts, kept rather than counted: threads and unread threads per label (and `ALL` for All Mail), and unread inbox threads grouped by the other tabs' categories they carry (Inbox, each tab and Primary are sums of these). `recompute_threads` adds each thread's change in the same transaction (`db/threads/counts.rs`); counting an 800,000-message mailbox took seconds per query
- `messages` — Full message data; `to_addresses`, `cc_addresses`, `raw_headers` as JSON; `fully_fetched = 0` means metadata only; `body_fetched_at` is when the cached body was downloaded (drives `body_retention`)
- `attachments` — Attachment metadata incl. `content_id`/`is_inline` (content is cached on disk, not stored); cascades from messages
- `outbox` / `outbox_messages` — Ordered queue of local changes and sends waiting for Gmail, with each target message's labels before the change
- `sync_state` — Per-account backfill position
- `contacts` — Every address an account has exchanged mail with (sent/received counts, last dates), kept by a trigger on `messages`, for recipient suggestions
- `google_contacts` / `google_contacts_sync` — The account's downloaded Google Contacts (name, first phone, organization, chosen photo) and how the last download went
- `calendars` / `events` — Each account's Google calendars (with `hidden`, Pheeme's local sidebar tick, and the sync token) and their events; a repeating event is stored once (`recurrence`) with its changed or cancelled occurrences (`recurring_event_id`), and expanded when read
- `calendar_reminders_fired` — Event reminders already shown (or dropped for the schedule), per occurrence and lead time, so a restart never shows one twice; pruned after 2 days
- `calendar_access` — Per account: whether calendar access was allowed and how the last calendar sync went, plus the user's Calendar time zone and week start
- `task_lists` / `tasks` — Each account's Google Tasks lists (with `hidden`, Pheeme's local sidebar tick, and the poll mark `synced_through_ms` / `full_synced_at`) and their tasks (parent, position, notes, due date, status, raw JSON)
- `tasks_access` — Per account: whether its tasks can be read (`api_disabled` means the Tasks API is off) and when they last synced, kept apart from `calendar_access`
- `app_settings` — App-wide preferences the Rust side needs before the window loads, one text row per setting (`db/settings.rs`: Gmail quota pace, tray icon, telemetry and its install ID, notification schedule, calendar reminders, assistant switches, per-account hidden inbox tabs and signature choices, the resync position)
- `notification_settings` — Per account: whether new-mail notifications are on (`db/desktop.rs`); cascades from accounts
- `recent_searches` — The last 20 searches, newest first (`db/search.rs`)
- `event_templates` — Calendar event templates: a name (unique ignoring case) and the event's details apart from its time as JSON (`TemplateFields`), local only (`db/templates.rs`, `calendar/templates.rs`)
- `usage_counts` — Anonymous usage counts per local day, kind (`screen`, `key`, `palette`, `button`) and name, waiting for the daily usage report (`db/usage.rs`, `telemetry.rs`)
- `assistant_clients` / `assistant_activity` — Connected MCP clients (token hashes) and their latest 1,000 tool calls with arguments and results

## Key Conventions

- **One-to-one with Gmail or not at all:** a mail feature that Gmail also has (snooze, scheduled send, and the like) either matches Gmail exactly, showing and changing the same state on every device, or Pheeme doesn't have it. No local-only stand-ins that other devices can't see. Where the Gmail API can't reach the feature, hand off to Gmail itself (for example, Send later saves the draft and opens Gmail's Drafts on the web) instead of imitating it.
- **IPC pattern:** Add a Rust fn in `commands/<domain>.rs`, register it in `lib.rs`'s `Builder`, add the command to the `Commands` map in `src/lib/ipc/commands.ts` (name, `args`, `result`) and a wrapper over `call` in its domain file under `src/lib/ipc/` (or the feature's `api.ts`). Then give the browser preview a fake in `src/preview/`: `createPreviewHandlers` is typed against `Commands`, so it fails typecheck until the command is faked. A new event goes in `AppEvents`; listen with `listen` from `src/lib/tauri`, never `@tauri-apps/api/event` directly.
- **DB queries:** Use `sqlx::query_as!` macros for compile-time checking. All queries go in `db/<entity>.rs`.
- **Thread labels** live in the `thread_labels` table, derived from `messages.label_ids`: change message labels, then call `recompute_threads` in the same transaction.
- **Mail changes** (archive, read, star, trash, send) go through `sync::outbox`, never straight to Gmail (drafts are the exception: saved straight to the drafts API). Write transactions use `db::begin_write` (`BEGIN IMMEDIATE`).
- **Label metadata changes** (create, rename, delete, colour, visibility) go straight to Gmail through `LabelService` (`labels.rs`), not the outbox, and hold the per-account label lock. Label sync takes that lock with `try_lock`, so message sync never waits on it.
- **AI assistant tools** go in `local_api` (a `Request` variant and a `catalog` entry, side by side), calling a service; the MCP layer never needs to change. Keep writes to the outbox and services the UI uses.
- **User-initiated Gmail calls** (label, draft and search commands, outbox dispatch) run inside `gmail::user_action`, ahead of sync and the backfill: wrap any new command that calls Gmail the same way.
- **Calendar and Tasks data commands** (those that read or change events, calendars, tasks or Google) run inside `commands/timing.rs`'s `Call` (`Call::write`/`Call::read(area, op)`), which logs each one's time split into Google's and Pheeme's (`calendar write`, `tasks read`, …); wrap a new one the same way. The window adds `calendar write shown` (`src/calendar/writeTiming.ts`) for each change it waits on.
- **Command errors** reject with `{ code, message }` (`CommandError` in `commands/mod.rs`): branch on `code`, show `message`.
- **No layout shift when data loads:** a component must have the same size and the same elements before and after its data arrives. Render every line, button and value slot from the first frame, with a `Skeleton` (`src/components/ui/Skeleton.tsx`) or placeholder in place of the missing value; don't add or remove elements (`{data && …}`) once it loads. Messages about empty or missing data ("no network", "no results") show only after the load has finished, never during it: keep "not loaded yet" (`null`) apart from "loaded and empty" (`[]`).
- **Onboarding guide text** lives in `src/onboarding/steps.ts` and is mirrored in `docs/google-cloud-setup.md`; change both together.
- Tauri dev server runs on **port 1420** (HMR on 1421). Don't change these without updating `tauri.conf.json`.

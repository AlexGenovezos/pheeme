# Release Pipeline + Test Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pushing a `vX.Y.Z` tag builds Pheeme for macOS, Windows and Linux on GitHub Actions and publishes a GitHub Release with updater artifacts, and the existing code carries real regression tests (Rust and frontend) with coverage reported in CI.

**Architecture:** One tag-triggered `release.yml` built on `tauri-apps/tauri-action`, which also dry-runs (build only, no publish) on PRs that touch release files. The app gets `tauri-plugin-updater` + `tauri-plugin-process`. A small framework-free `src/lib/updater.ts` holds the check/apply logic, tested with injected fakes, and a tiny `UpdateBanner` offers "Restart to update". Versions live in three files, which `scripts/version.mjs` keeps in sync; a test and the release job both enforce that. Test hardening adds the missing Rust tests from the Claude review of Tasks 4–8, a jsdom Vitest setup with real frontend tests, and a coverage job.

**Tech Stack:** GitHub Actions, `tauri-apps/tauri-action` (latest release is `action-v1.0.0`; use its current major tag and read its README for input names), `tauri-plugin-updater` 2, `tauri-plugin-process` 2, Vitest 2 + jsdom + @testing-library/react, `@vitest/coverage-v8`, `cargo-llvm-cov`.

**Spec:** `docs/superpowers/specs/2026-10-31-mail-calendar-client-design.md` §7 (release pipeline), §11 (testing). This plan pulls §12 step 12 forward at Alex's request (2026-11-01). Cross-platform QA of real features stays in step 12.

## Review Focus

1. **Tag and app version disagree** (tag `v0.2.0`, but `tauri.conf.json` says `0.1.0`). Expect: the release fails before building, with a message naming both versions. → Task 6 (test) and Task 8 (workflow guard).
2. **Apple secrets missing or partial** (cert set, notarization password missing). Expect: the macOS job builds unsigned and warns. It never fails half-signed, and secrets never print. → Task 8 (`scripts/resolve-apple-env.test.sh`).
3. **The update check fails** (offline, GitHub 404 on a private repo, bad signature). Expect: the app runs normally with no banner and no unhandled rejection; the error is logged once per check. → Task 7 (`updater.test.ts`).
4. **The user ignores the update banner, or the periodic check fires again while a download is running.** Expect: one in-flight check or download at a time; the banner stays put and isn't duplicated. → Task 7.
5. **A PR edits release.yml.** Expect: a dry-run build with no publish and no secrets, so a broken pipeline is caught before a tag. → Task 8.

  ```ts
    relaunch(): Promise<void>;                // prod: @tauri-apps/plugin-process relaunch()
    log(msg: string, err: unknown): void;     // prod: console.error
  }
  export const CHECK_INTERVAL_MS = 6 * 60 * 60 * 1000;
  export const useUpdateStore: zustand store { available: string | null; applying: boolean; apply(): Promise<void> }
  export function startUpdateChecks(deps?: UpdaterDeps, intervalMs?: number): () => void; // returns stop
  ```
  Behavior:
  - Check immediately, then every `intervalMs`.
  - A check is skipped while a previous one is still running, or once an update is already `available`.
  - A found update is stored: `available = version`, plus the `PendingUpdate` in a module variable.
  - `apply()` sets `applying`, awaits `install()` then `relaunch()`, and is a no-op while `applying`. On failure it logs, resets `applying`, and keeps `available`.
  - Check errors are logged and swallowed.
  - Nothing downloads until the user clicks. This avoids the Windows installer appearing unasked.
  - Platform note, to put in a code comment: on Windows, `install()` launches the NSIS installer and exits the app, so `relaunch()` is never reached. The tests prove the controller's ordering, not Windows behavior.
- `UpdateBanner`: renders nothing when `available` is null. Otherwise it shows `Pheeme {version} is ready` and a button `Restart to update` (disabled and labelled `Updating…` while `applying`).
